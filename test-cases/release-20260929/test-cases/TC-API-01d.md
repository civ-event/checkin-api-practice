# TC-API-01d: 不能用宿主机日期断言业务日

| 属性 | 值 |
|------|-----|
| 编号 | TC-API-01d |
| 优先级 | P0 |
| 模块 | 时钟 |
| 平台 | Server |
| 关联需求 | 业务日来自容器时钟和配置时区 |
| 关联 CR | CR-1 Negative；7.4 第一条 |

## 前置条件

- Compose 仍保留 `FAKETIME`。不要为了本条改环境变量。
- 宿主机真实日期早于 2026-10-10，或至少与容器 `date` 不是同一天。当前练习日在 2026-09 时满足。

## 操作步骤

1. 宿主机执行 `date +%Y-%m-%d`，记为 H。
2. 容器执行 `php -r 'echo date("Y-m-d");'`，记为 C。
3. 用 C 的游戏时区日期（TC-API-01 第 2 步）对照签到 status 的 `yearMonth` 和 `maxAvailableDay`。
4. 不要修改 `activities.php`。直接再查一次 `activity_id=1` 的签到 status。

## 预期结果

- H 与 C 不是同一天。C 落在假时钟的 2026-10（或启动后流逝所到达的月份），H 若仍是 2026-09，则月份不同。
- `yearMonth` 由游戏时区的 C 决定，不由 H 决定。
- 第 4 步 HTTP 200。窗口是 `2026-09-01 00:00:00` 到 `2026-10-31 23:59:59`，假时钟停在 10 月内时活动正在进行。
- 若有人把假时钟调到 `2026-11-01`（本条不要求这么做），才会 HTTP 404，`ACTIVITY_NOT_FOUND`，消息 `Activity is not running`。

## 不应出现

- 因为宿主机是 9 月 29 日，就预期 `yearMonth=202609` 或 `ACTIVITY_NOT_FOUND`。
- 用「活动结束日已经从 9 月 30 日改到 10 月 31 日」代替时钟检查。窗口延长被 CR-1 盖住，本条两种都要看：时钟是假的，窗口按假时钟判断。

## 备注

- 去掉 `FAKETIME` 后重启，`date` 应与宿主机同一天。那是 CR-1 建议的修复验证，不是当前练习环境的通过条件。当前通过条件是：容器日期与宿主机日期分开，且接口跟容器。
