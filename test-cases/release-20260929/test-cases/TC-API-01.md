# TC-API-01: 容器业务时间从 2026-10-10 17:00 UTC 起算并继续走

| 属性 | 值 |
|------|-----|
| 编号 | TC-API-01 |
| 优先级 | P0 |
| 模块 | 时钟 |
| 平台 | Server |
| 关联需求 | 练习环境用 libfaketime。签到、活动窗口用游戏时区；累充当月用角色服务器时区 |
| 关联 CR | CR-1 Happy；7.3 草案。草案写「日期永远是 2026-10-10」，与 `@` 前缀不符，以本条为准 |

## 前置条件

- 使用仓库里的 `docker-compose.yml` 启动，未删除 `LD_PRELOAD` 和 `FAKETIME=@2026-10-10 17:00:00`。
- PHP 默认时区是 `Asia/Shanghai`（`docker/php/php.ini`）。
- 这是练习时钟。用户已决定本地练习保留它。本条确认现状，不是要求改成宿主机时间。

## 操作步骤

1. 在宿主机执行 `date +%Y-%m-%d`。
2. 在 app 容器执行 `php -r 'echo date("Y-m-d H:i:s"), PHP_EOL, (new DateTimeImmutable("now", new DateTimeZone("Etc/GMT+5")))->format("Y-m-d H:i:s"), PHP_EOL;'`。
3. 用角色丁查签到 status，`activity_id=1`。
4. 用角色乙查累充 status，`activity_id=2`。

## 预期结果

- 容器刚启动时，Unix 时间对应 `2026-10-10 17:00:00` UTC。上海时间从 `2026-10-11 01:00:00` 起算，游戏时区 `Etc/GMT+5` 从 `2026-10-10 12:00:00` 起算。之后按真实流逝增加，不是停住。
- 第 2 步的上海日期不是第 1 步的宿主机日期（执行日若仍是 2026-09，月份就不同）。
- 签到 `yearMonth` 等于第 2 步游戏时区日期的 `Ym`。仍在 10 月时为 `202610`。
- 累充 `yearMonth` 等于该角色服务器时区的 `Ym`。乙是 `Asia/Shanghai`，丁的签到仍用游戏时区。10 月内两边都是 `202610`。
- `maxAvailableDay` 等于游戏时区「日」，且不超过 31。刚启动、游戏时区仍是 10 月 10 日时为 10。时钟走过几天后变为当天的「日」，不要再断言永远是 10。

## 不应出现

- 断言 `date()` 永远等于 `2026-10-10`。`FAKETIME` 带 `@`，启动后会走。
- 用宿主机「今天是 9 月 29 日」解释签到第几天，或认为活动已在 9 月 30 日结束。活动窗口到 `2026-10-31 23:59:59`。
- 把这只练习时钟说成已经对齐线上时钟。

## 备注

- CR-1 作为上线配置仍是 P0：默认 Compose 带着 faketime。练习发布说明里必须写明。本条不要求删掉这两行环境变量。
- 已有自动化：`tests/Clock/ContainerClockTest.php` 只断言 `Y-m` 为 `2026-10`。容器时钟离开 10 月后该测试会失败，需要另看本条的「游戏时区 Ym」。
- 重启后时钟跳回锚点、库里的签到时间落到未来，见 TC-API-01b。
